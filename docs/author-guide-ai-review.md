# Гайд автора: AI-проверка заданий

AI-проверка — это автоматический ревью PR-а студента на GitHub, который
дополняет (а не заменяет) твою ручную проверку. AI читает diff, инструкции
от тебя и пишет inline-комменты + summary прямо в PR.

## Когда AI-проверка работает

1. У студента есть PR на GitHub в репозиторий, к которому подключён твой GitHub App.
2. Submission задания pushed в платформу.
3. Студент или ты нажимаешь **«Запустить AI»**.
4. Через ~30-90 сек в PR появляется review-комментарий.

AI **никогда** не блокирует merge — все ревью идут как `event=COMMENT`,
не `REQUEST_CHANGES`. Студент решает, что делать с фидбэком.

## Две точки конфигурации

### 1. PROJECT-level: общие guidelines

Открывается на странице курса → проект → ⋯ → **AI-проверка**.

Это markdown-инструкции для AI, которые **применяются ко всем заданиям проекта**.
Туда нужны вещи общие для всего проекта:

- Стиль кода (naming, formatting, организация файлов)
- Обязательные тесты
- Архитектурные правила (например, «никаких exceptions для бизнес-ошибок»)
- Формат коммитов
- Документация (XML-docs, JSDoc, etc.)

Пример хороших guidelines:

```markdown
# .NET Backend Guidelines

- Все public-методы имеют XML-docs с описанием и параметрами
- Бизнес-ошибки возвращаются через `Result<T, Error>`, не через throw
- DTO не утекают наружу domain entities (см. CLAUDE.md → DI Pattern)
- Каждый Handler покрыт integration-тестом
- Migration files immutable — fix через новую миграцию
```

Toggle **«Включить AI-проверку для проекта»** — выключи если временно
не хочешь, чтобы студенты дёргали AI (например, во время exam-периода).

### 2. ISSUE-level: per-task spec

Открывается в edit-issue sheet → секция **AI-проверка** внизу.

Тут две textarea:

**Инструкции для AI** — что AI должен знать про *конкретно эту задачу*.
Прячь детали реализации, направляй внимание:

> «Это задача про event-driven архитектуру. Проверь, что publish и
> SaveChanges идут через `ITransactionManager`. Не должно быть прямых
> `_db.SaveChangesAsync()` в handler'ах.»

**На что обратить внимание** — конкретные аспекты, на которых хочешь
сфокусировать проверку:

> «Тесты на edge cases. Идемпотентность. Логирование ошибок.»

Toggle **«Кнопка "Запустить AI" для студента»** — выключи чтобы временно
скрыть AI у конкретной задачи (например, задача creative, проверять руками).

## Cost-aware tips

DeepSeek V4 Pro (default) — дёшево, но не бесплатно. Лимиты:

- Diff > 1500 строк добавлений — AI отказывается (`review.diff.too_large`).
  Попроси студента разбить PR.
- Per-user/day cap — 100 итераций.
- Per-submission cap — 20 итераций.

**Чтобы не палить токены зря:**

- Короткий prompt > длинный. AI лучше работает с конкретикой, не с простынёй.
- Не дублируй PROJECT guidelines в ISSUE spec — оба попадут в prompt.
- Idempotency: повторный run на тот же commit_sha возвращает результат
  предыдущей COMPLETED-итерации без LLM-вызова.
- Draft PR не принимаются — попроси студента нажать «Ready for review».

## Когда AI ошибается

AI несовершенен — поэтому он не блокирует merge. Если AI пишет ерунду:

1. Ты можешь добавить уточнение в issue spec («Игнорируй паттерн X — это by design»).
2. Можешь переключить модель в админке (`/admin/ai-models`) на более сильную
   (Claude Sonnet 4.6) для конкретного запуска (admin override).
3. Если систематически плохо — добавь правило в PROJECT guidelines.
